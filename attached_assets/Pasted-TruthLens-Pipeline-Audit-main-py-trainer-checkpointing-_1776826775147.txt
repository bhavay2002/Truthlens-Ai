TruthLens Pipeline Audit — main.py → trainer → checkpointing → drive sync
🔴 CRITICAL — must fix before next training run
C1. save_model in main.py is a silent‑data‑loss machine (lines 207‑244)
Root cause. Three independent failure modes stacked on top of each other:

save_thread writes pytorch_model.bin asynchronously.
copy_thread is started immediately after and runs LOCAL_SAVE_PATH.iterdir() — so it can copy before pytorch_model.bin is written and before config.json exists (config.json is written on the main thread after the copy thread starts).
Both threads are daemon=True joined with timeout=10. A 400 MB model on a slow Colab disk takes 30‑60 s. The function returns "successfully" with no error while the save is aborted at interpreter shutdown.
There is also no atomic write (no .tmp → rename), no per‑file integrity check, no per‑file exception handling, and no "best model only" logic — every call clobbers the previous artifact.

Fix. Make saves synchronous, atomic, ordered, and verified:

# main.py — replace save_model
def save_model(model, tokenizer):
    create_folder(LOCAL_SAVE_PATH)
    tmp = LOCAL_SAVE_PATH / "pytorch_model.bin.tmp"
    final = LOCAL_SAVE_PATH / "pytorch_model.bin"
    state = {k: v.detach().cpu() for k, v in model.state_dict().items()}
    for k, v in state.items():
        if torch.is_tensor(v) and not torch.isfinite(v).all():
            raise RuntimeError(f"Refusing to save: non-finite values in {k}")
    torch.save(state, tmp)
    os.replace(tmp, final)
    tokenizer.save_pretrained(str(LOCAL_SAVE_PATH))
    save_json(
        {"model_type": "multitask_truthlens",
         "architectures": ["MultiTaskTruthLensModel"]},
        LOCAL_SAVE_PATH / "config.json", indent=2,
    )
    logger.info("Local save complete: %s", final)
    # Drive sync: only AFTER local save is durable
    if DRIVE_SAVE_PATH.exists() or DRIVE_SAVE_PATH.parent.exists():
        _sync_to_drive(LOCAL_SAVE_PATH, DRIVE_SAVE_PATH)
def _sync_to_drive(src: Path, dst: Path, retries: int = 3) -> None:
    create_folder(dst)
    for f in src.iterdir():
        target = dst / f.name
        for attempt in range(1, retries + 1):
            try:
                shutil.copy2(f, target.with_suffix(target.suffix + ".tmp"))
                os.replace(target.with_suffix(target.suffix + ".tmp"), target)
                if target.stat().st_size != f.stat().st_size:
                    raise IOError(f"Size mismatch after copy: {target}")
                break
            except Exception as exc:
                logger.warning("Drive copy attempt %d/%d failed for %s: %s",
                               attempt, retries, f.name, exc)
                if attempt == retries:
                    raise RuntimeError(f"Drive sync failed for {f.name}") from exc

            history["val_loss"].append(val_loss)

                optimizer=self.optimizer, scheduler=self.scheduler,

                    save_every=1, deduplicate=False,

M6. _train_epoch continues on NaN but already incremented global_step and queued work (trainer.py:280-291)
if not torch.isfinite(raw_loss):
    logger.error("NaN/Inf loss detected at step %d", step); continue
loss_accum = ...; step_count += 1; self.global_step += 1

That ordering looks right (the continue happens before the increment), but loss = raw_loss / grad_accum and the autocast block already ran the forward/backward graph. With set_to_none=True, optimizer.zero_grad doesn't run on the next iteration unless (step+1) % accum == 0, so a NaN halfway through an accumulation window leaves the optimizer holding poisoned grads from the steps before the NaN. Also: after continue, the very next valid step has the previous partial accumulation grads still in the buckets.

Fix. Treat NaN as a reset of the accumulation cycle:

if not torch.isfinite(raw_loss):
    logger.error("NaN/Inf loss at step %d — resetting accumulation", step)
    self.optimizer.zero_grad(set_to_none=True)
    continue
